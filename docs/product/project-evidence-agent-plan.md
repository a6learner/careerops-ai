## 1. 要交付的产品

面向使用代码助手做项目、正在准备 SWE/backend/AI 岗位的个人开发者。
开发过程中保存带来源的项目记录，求职时按目标要求找回项目细节，生成可审核的
简历要点和面试讲述素材。用户继续使用自己的代码助手和模型；新增记录路径由
CareerOps 提供结构化存储、检索、校验和展示，不在服务端新增模型调用。

第一版成功场景：

1. 用户把一个本地项目关联到自己的 CareerOps 项目档案，可选关联一个岗位 gap。
2. 在一个功能、bug 修复或验证阶段结束时，宿主代码助手按 Skill 整理 checkpoint。
3. 记录保留问题、改动、设计取舍、失败过程、验证依据、待办和个人贡献说明。
4. MCP 写入草稿并返回持久化回执；用户在网页审核，必要时纠正。
5. 换一个会话，助手能搜索已确认记录、读取原始依据，重建项目讲述。
6. 用户选择目标岗位后，助手生成有引用的简历要点和 STAR 草稿；无依据的指标不生成。

第一版必须能在 Windows 本地运行，并完成一次真实宿主接入演示。
它是宿主驱动的 agent 扩展，不宣称有一个独立后台自主运行的 agent。

## 3. 范围与暂缓项

### 第一版必须有

- Project：用户拥有的项目档案；不要求公开 GitHub 仓库。
- Checkpoint：按开发阶段记录，而不是每一行代码或每次聊天都写日志。
- Evidence：保存选定、限量的代码/文档摘录与验证依据，能够跨会话读取。
- Review：区分自动草稿、用户确认、撤回/替代记录。
- Retrieval：先做按项目、关键词、技术主题、阶段筛选和稳定分页。
- Career brief：宿主模型基于返回记录生成简历与面试草稿，引用来源。
- 一个标准 MCP 接口、一份记录 Skill、一套本地运行说明。
- 以 Codex 为首个宿主的真实接入验收；Claude Code 作为第二宿主兼容性检查。
  每个宿主的实际能力和版本分别记录，不保证“一份安装配置通用”。
- 对本项目立即使用相同记录模板：在产品未完成前，先用现有 ADR、learning、metrics
  留下开发过程；产品可用后再验证导入，避免为开发记录创建并行事实源。

### 暂缓

- 学习计划、课程搜索、每日自主跟进、任务调度和多 agent。
- Notion 双向同步、GitHub OAuth/PR 自动采集、云端远程 MCP 公共服务。
- 所有 IDE 的自动 hooks 适配、完整聊天历史上传、全仓库监听或全量上传。
- 自动执行用户代码、自动运行任意 shell、自动验证任意 URL、自动创建简历正向声明。
- 新向量检索、LangGraph/LangChain、独立模型网关、用户 API key 托管。
- 自动把开发记录写成正式 Experience；第一版先导出审核后的素材。

学习计划与 Notion 是 V2 候选，不纳入本日程承诺。

## 4. 用户实际操作与触发方式

建议命令意图：初始化项目、记录本阶段、回顾项目、按职位准备素材。
名称与宿主安装格式在 K1 的接入设计中冻结。

第一版是“可明确触发的阶段记录 + Skill 自动建议”，不承诺永不遗漏。
Skill/MCP 不是监听器；如果宿主没有触发、发生崩溃或上下文不可用，就可能缺记录。
用户必须能一键/一条指令补记，并看到上次成功记录的时间和范围。
正式阶段边界由项目活动决定，例如完成一个功能、定位一个失败、选定一个 ADR、
完成一轮验证，不要求提交 Git 后才记录。

对手写代码同样可用：助手读取选定变更再补记，但无法恢复没有记录的设计动机。
对旧项目只支持明确标记为“事后重建”的回顾，不将推断伪装成当时发生的事实。

## 5. 记录合同与证据边界

每条 checkpoint 至少包含：

| 内容 | 要求 |
|---|---|
| 身份 | project、采集时间、宿主、schema/Skill 版本、幂等键 |
| 输入范围 | 基础 commit、选定文件和变更摘要；未提交内容使用独立内容摘要 |
| 问题与行动 | 目标、实际改动、理由、替代方案、失败及修复 |
| 结果 | 已验证行为、尚未验证内容、剩余风险；无结果时明确为空或未知 |
| 来源 | 相对路径、commit/内容 hash、引用摘录、来源类型；必要时带行号 |
| 验证 | 命令、退出码、输出摘录/工件及条件，注明机器采集或用户/模型转述 |
| 个人贡献 | 用户确认的负责范围、AI 参与情况、尚需理解的概念 |
| 审核 | draft/confirmed/withdrawn、审核时间、替代关系 |

信任等级分开呈现：模型总结、用户陈述、提供的工件、可核对的验证记录。
hash 能证明内容一致性，不能证明测试真的运行、成果真实或代码由本人编写。
远端服务不能仅凭客户端声明就将测试标成“服务端验证通过”。

不只保存会漂移的行号：保存足以追溯的、经过选择的来源快照/摘录和内容 hash。
如果摘录不足以支持结论，保留“依据不足”，不做补全。外部链接不可访问时保持
unverified，不自动抓取。采集时不读取 `.env`、凭证、聊天全量或不相关目录；
上传前展示范围，允许删减。K1 冻结允许的来源、大小/数量限制和保留删除策略。

个人贡献不从 Git author 或模型生成记录推断。用户确认“负责了什么”和“理解什么”
也不自动转化为能力认证。课程完成、任务打勾、代码存在分别记录。

## 6. 生命周期、事务、幂等与恢复

业务审核生命周期：`draft -> confirmed -> withdrawn`，也允许 `draft -> withdrawn`。
已确认记录内容保留历史；初片纠错方式是撤回后新建草稿，不原地改写证据。
显式替代关系留待后续。撤回保留之前的个人贡献说明，但不能作为当前正向依据。
现阶段没有 DELETE/自动清理，撤回不是隐私擦除；公开发布前需要补齐删除管理。

一次写入原子保存 checkpoint、来源和幂等记录，数据库约束保护所有权和引用。
同一用户、同一幂等键、同一规范化载荷返回相同记录；同键不同载荷明确冲突。
并发重试只产生一条记录。未收到回执时，用同键查询/重试，不宣布保存成功。

采集端允许保留待发送包及接收回执；包不是服务端已接受记录，也不是第二事实源。
断网时明确显示 pending，恢复后重放相同载荷。删除/撤回后的旧重放不能复活数据。
K1 必须明确幂等墓碑保留及个人数据删除边界，再决定是否实现自动重放。

首版 MCP 建议本地 stdio 薄适配器，调用既有 API/service 层，不绕过授权直连数据库。
本地路径由宿主/采集端处理；API 不接收路径后读取服务器文件。
本地新工具路径不调用模型。现有 worker LLM 流程和 opt-in 继续保持原边界。

初版工具草案（6 个，具体 schema 待 K1）：

| 工具 | 结果 |
|---|---|
| `list_projects` | 查找自己可访问的项目 |
| `register_project` | 幂等创建项目档案，不自动扫描或上传仓库 |
| `get_project_context` | 读取目标、最近记录、未完成事项 |
| `save_checkpoint` | 校验后保存草稿，返回 ID、hash、审核状态和回执 |
| `search_project_evidence` | 限定项目/主题搜索，返回稳定记录 ID 和摘要 |
| `get_evidence` | 返回授权范围内的详细记录和来源 |

确认、撤回和管理先通过网页/API 明确操作。工具不代用户确认个人贡献。
认证初步复用现有账户；宿主认证交接、token 保存、30 分钟过期后的重登录方式
必须先设计和验证，不把前端 HttpOnly cookie 暴露给模型，不把 token 写入 Skill。

## 7. 数据模型与实现落点（提案）

首片采用 `projects`、`project_checkpoints` 两张表；来源以有上限的 JSONB
与 checkpoint 原子存储，不新增可独立变更的来源表。具体合同见 ADR-041。
第一版不修改既有 Experience/Analysis verdict 语义，不为项目记录触发 embedding。
项目可关联用户自己的岗位/gap，删除、归档、撤回时的引用语义在 K1 明确。

预计涉及：

- `src/careerops/{api,schemas,domain,services,repositories}/` 下的 project/evidence 模块。
- `src/careerops/db/models.py`、`migrations/versions/`：仅在设计批准后新增。
- MCP 薄适配器、Skill、采集脚本目录：K1 确定，避免嵌入工具个人配置。
- `frontend/src/`：项目列表、checkpoint 审核、证据检索与复制/导出。
- `tests/`、`frontend/e2e/`：新增行为和必要回归。
- `README.md`、ADR、learning、metrics：随对应实现更新。

不引入新数据库或微服务。MCP SDK 如需新增依赖，先提交具体版本、体积/维护影响和
替代方案；不为了省依赖手写未经验证的协议实现。

## 9. 验证方案与完成定义

静态/自动：严格 mypy、Ruff、import boundaries；新增 unit、PostgreSQL integration、
授权与并发测试；frontend lint/typecheck/component/build；MCP schema 与错误契约测试。
开发时运行受影响测试；阶段结束做对应集成，K8 做完整质量门禁和 fresh migration/drift。
不重复冻结 embedding/matcher holdout，不因失败删减旧断言。

必须直接验证：

- 同键同载荷重放、同键不同载荷冲突、同时保存、事务中途失败。
- 跨用户 project/source/record 访问、伪造关联 ID 和越权引用。
- 超时后回执丢失、断网、进程退出、重放、过期认证和恢复后的状态一致性。
- 引用路径移动、未提交内容、来源缺失、记录纠错/撤回及删除后的重放。
- secret-like 输入、超限附件、提示注入文本；源码/记录内容只作为数据处理。
- 草稿不能直接成为已确认求职事实；模型自述通过不能冒充真实测试结果。

Agent 验证分两层：CI 用 fake 宿主/固定工具轨迹保证不联网、不付费；
真实宿主验收使用作者已有模型和明确批准的合成/自有数据，不代收模型 key。
记录宿主、版本、模型（可获得时）、时间、调用轨迹、原始输出和评价。
真实工具调用失败不能用 fake 演示替代并称兼容通过。

K7 新建独立评估集，覆盖从材料充分到证据不足、个人贡献不明、指标无来源、
记录撤回、重复和冲突等情况；从未参加既有冻结 holdout。
比较“仅看仓库回顾”和“使用 checkpoint 回顾”的事实找回、来源支持、
无依据指标、贡献过度推断、恢复/去重结果。人工评分规则先冻结再跑，
公开每个案例和分母；目标是核心安全案例全部通过，其余如实报告，不提前许诺提升。
耗时、tokens、成本只能来自实际可获取数据，否则 `not measured`。

K8 核心场景：新环境启动→登录→关联项目→宿主保存记录→网页确认→
新会话检索→按岗位要求生成带引用的素材→用户发现错误并撤回→再次检索正确处理。
另外演示一次“已提交但回执丢失”的恢复。不能依赖直接改数据库完成验收。

延后回顾实验：K4 开始积累本人项目记录，至少在另一个开发会话尝试重建背景、取舍、
验证和贡献。到 K7 记录实际间隔与缺漏；尚未经过一周就不能声称“一周后仍完整找回”。

## 10. 每个关键节点必须留下的开发记录

每个 K 节点结束前，开发助手必须更新如下权威位置，不能只在聊天说完成：

| 记录 | 位置与要求 |
